# แผนทดลองกล้องวงจรปิด IMOU (IPC-A26LP / Rex) — วัด "นั่งผิดบ่อยแค่ไหน" รายโต๊ะ

> สถานะ: **ร่าง — รออนุมัติ ยังไม่เริ่มทำ** (2026-10-06)
> เป้าหมาย POC: กล้อง 1 ตัว ดู 2–4 โต๊ะ → รู้ว่าแต่ละโต๊ะนั่งท่าไม่ดีกี่ % ของเวลา และระบบแม่นพอใช้จริงไหม
> หลักการ: หน้าเดิม `/` และ logic ตรวจจับเดิมต้องไม่เปลี่ยน · ไม่เก็บภาพ/วิดีโอ · สถิติรายโต๊ะ ไม่ระบุตัวคน

---

## 0. ข้อมูลกล้อง (จากเอกสารผู้ขาย — ต้องยืนยันกับเครื่องจริง)

- 2MP 1920×1080 สูงสุด 25/30 fps · H.264/H.265 · เลนส์ 3.6 mm · pan-tilt · Wi-Fi
- รองรับ RTSP + ONVIF — URL แบบ Dahua:
  ```
  rtsp://admin:<Safety Code>@<IP>:554/cam/realmonitor?channel=1&subtype=0   ← main 1080p
  rtsp://admin:<Safety Code>@<IP>:554/cam/realmonitor?channel=1&subtype=1   ← sub (ความละเอียดต่ำ)
  ```

## 1. สถาปัตยกรรม POC

```
IMOU ──RTSP──▶ go2rtc (เครื่องเดียวกับ dev server, :1984)
                 │  แปลง H.264 → MJPEG (ใช้ ffmpeg)
                 ▼
Vite dev server (:5173)  proxy /go2rtc → localhost:1984   ← ทำให้เป็น origin เดียวกับแอป
                 │
                 ▼
แอป: แหล่งภาพ "กล้อง IP (MJPEG)" เดิม = /go2rtc/api/stream.mjpeg?src=imou
     → CameraStage → PostureEngine (โค้ดเดิมทั้งหมด)
```

ทำไมแบบนี้:
- แอปรองรับกล้อง IP แบบ MJPEG ผ่าน `<img>` อยู่แล้ว (`CameraSourceSelector` → `CameraStage`) — **ขั้นแรกไม่ต้องแก้โค้ดแอปเลย**
- ปัญหา CORS เดิม (canvas tainted) หายเพราะ proxy ทำให้ภาพมาจาก origin เดียวกับแอป
- MJPEG ง่ายที่สุด แลกกับใช้ CPU แปลงภาพและแบนด์วิดท์สูงกว่า WebRTC — พอสำหรับกล้อง 1 ตัว

## 2. ขั้นตอน

### ขั้น 1 — ดึงภาพให้ได้ (ผู้ใช้ทำ + config 1 จุด)
ผู้ใช้:
1. แอป Imou Life → เปิด RTSP/ONVIF · ปิด TLS ถ้ามีเมนู · **ปิด auto tracking / ล็อกตำแหน่ง pan-tilt**
2. ตั้ง IP กล้องแบบคงที่ (DHCP reservation ที่ router) กัน IP เปลี่ยน
3. ทดสอบ URL ใน VLC ให้เห็นภาพ
4. ติดตั้ง go2rtc + ffmpeg บนเครื่อง dev แล้วตั้ง `go2rtc.yaml`:
   ```yaml
   streams:
     imou: ffmpeg:rtsp://admin:<Safety Code>@<IP>:554/cam/realmonitor?channel=1&subtype=0#video=mjpeg
   ```
   ⚠️ ไฟล์นี้มีรหัสกล้อง — ห้าม commit (เก็บนอก repo หรือใส่ .gitignore)

โค้ด:
- `vite.config.ts` เพิ่ม `server.proxy['/go2rtc'] → http://localhost:1984` (rewrite ตัด prefix) — กระทบแค่ dev server

ตรวจผ่านเมื่อ: `/?console` → เพิ่มกล้อง → แหล่งภาพ IP → ใส่ `/go2rtc/api/stream.mjpeg?src=imou` → เห็นภาพ + skeleton + ค่า ms (ไม่มี error CORS)

### ขั้น 2 — ประเมินมุมกล้อง (ยังไม่เขียนโค้ด)
1. วางกล้องจริงในออฟฟิศ — แนะนำ **มองโต๊ะจากด้านข้างเฉียง ระดับไม่สูงมาก** (เห็นยื่นคอ/หลังค่อมชัดที่สุด)
2. ดูใน console ด้วย Pose `full`/`heavy` + Skeleton `full`:
   - คนในภาพสูงพอไหม (คร่าวๆ ไหล่→หัวควรเกิน ~80–100 px)
   - จุด visibility ของหู/ไหล่/สะโพกนิ่งไหม โดนจอ/พาร์ทิชันบังแค่ไหน
   - ค่า ms ไหวไหม (งบ 83 ms/รอบ)
3. ส่งภาพหน้าจอให้ประเมินร่วมกัน → ตัดสินว่าไปต่อ / ย้ายมุม / เลิก

### ขั้น 3 — โซนโต๊ะ + สถิติรายโต๊ะ (โค้ดใหม่ใน Dev Console)
- **โซนโต๊ะ**: วาดสี่เหลี่ยมบนภาพกล้อง ตั้งชื่อ (เช่น "โต๊ะ A1") เก็บใน localStorage ต่อกล้อง
- **ผูกคนกับโต๊ะ**: ใช้ตำแหน่งกึ่งกลางไหล่ของแต่ละคน (มีอยู่แล้วใน `PostureEngine` เป็น `anchorPx`) ตกอยู่ในโซนไหน = โต๊ะนั้น
- **สถิติ**: ทุกเฟรมสะสมเวลาของแต่ละโต๊ะตามสถานะ `good / forward_head / slouching / leaning / ว่าง`
  → แสดงตาราง % เวลาที่นั่งผิด แยกตามท่า + จำนวนครั้งที่เข้าสู่ท่าผิด · Export JSON · ปุ่มรีเซ็ต
  (ยังเก็บในเบราว์เซอร์ — ส่ง backend เป็นขั้น 5)
- การแก้ไฟล์เดิม (แบบเพิ่มอย่างเดียว เหมือนรอบ Dev Console):
  - `CameraStage`: เพิ่มข้อมูล "ตำแหน่ง + สถานะท่ารายคน" ลงใน `onStats` (optional, ไม่ส่ง = เหมือนเดิม)
  - ไฟล์ใหม่: `src/lib/deskZones.ts` (หาว่าจุดอยู่โซนไหน + สะสมเวลา — มี test), `src/console/DeskZones*.tsx`
- ไม่แตะ `PostureEngine` / เกณฑ์ / การแจ้งเตือน

### ขั้น 4 — ปรับเกณฑ์ให้เข้ากับมุมกล้อง
- อัด dataset จากกล้อง IMOU ด้วย Recorder เดิม (เลือกกล้อง IMOU, ครบทุก label, หลายคน, ท่าละ 30–60 วินาที)
- วิเคราะห์แบบเดียวกับไฟล์ `camwell-dataset-2026-10-05T17-26-57.json` → เสนอเกณฑ์ใหม่พร้อมตัวเลขความแม่น
- **ต้องตัดสินใจ**: ตอนนี้เกณฑ์ใช้ร่วมกันทุกกล้อง — ถ้าใช้ webcam กับ IMOU พร้อมกัน อาจต้องทำ "เกณฑ์ต่อกล้อง" (แก้ logic → ขออนุมัติแยก)

### ขั้น 5 — นอกขอบเขต POC (วางแผนแยกเมื่อ POC ผ่าน)
- ส่งสถิติรายโต๊ะไป camwell-backend + dashboard
- รันแบบไม่ต้องเปิดเบราว์เซอร์ค้าง (inference ฝั่ง server)
- หลายกล้อง / ทั้งออฟฟิศ

## 3. เกณฑ์ว่า POC ผ่าน

1. ภาพจาก IMOU เข้าแอปได้ต่อเนื่อง ≥1 ชั่วโมงไม่หลุด
2. Pose ms ต่อรอบ < 83 ms ด้วยรุ่นที่เลือก
3. จับท่าได้แม่นพอ (ตัวเลขเป้าหมายตกลงกันหลังขั้น 4 — เช่น ท่าดีไม่แจ้งผิด และจับท่าไม่ดีได้ส่วนใหญ่)
4. ผูกคนกับโต๊ะถูกตลอดช่วงทดสอบ (ไม่สลับโต๊ะ)

## 4. ความเสี่ยง

| ความเสี่ยง | ผล | รับมือ |
|---|---|---|
| คนตัวเล็ก/โดนจอบัง | จับท่าไม่ได้หรือแกว่ง | ย้ายมุม, รุ่น heavy, ลดจำนวนโต๊ะต่อกล้อง |
| Wi-Fi กระตุก | ภาพค้าง, fall detection เข้าใจผิดว่าคน "หายจากเฟรม" | วางใกล้ router, ใช้ sub stream, ปิดเสียงเตือนหกล้มช่วงทดลอง |
| กล้องหมุน (pan-tilt) | โซนโต๊ะผิดที่ | ปิด auto tracking, ห้ามขยับ |
| ffmpeg แปลง 1080p กิน CPU | เครื่องช้า | ใช้ sub stream หรือ scale ใน go2rtc |
| เกณฑ์ปัจจุบันออกแบบสำหรับกล้องหน้าจอ | ผลเพี้ยนจากมุมกล้องวงจรปิด | ขั้น 4 |

## 5. PDPA / ความเป็นส่วนตัว

- แจ้งพนักงานที่อยู่ในมุมกล้องก่อนทดลอง และขอความยินยอมจากผู้ร่วมทดลอง
- ไม่บันทึกภาพ/วิดีโอ — เก็บแค่ตัวเลข (landmark, เวลาสะสมต่อโต๊ะ)
- สถิติรายโต๊ะ ไม่ใช้ face recognition ในงานนี้ (ปิดฟีเจอร์ใบหน้าตอนทดลอง)
- รหัสกล้อง (Safety Code) ไม่ commit ลง repo
- ก่อนใช้จริงทั้งออฟฟิศ ปรึกษา HR/ฝ่ายกฎหมาย

## 6. คำถามที่ต้องตอบก่อนเริ่ม

1. เครื่องที่จะรัน go2rtc + แอปช่วงทดลองคือเครื่องไหน (Windows เครื่องนี้?) ติดตั้ง ffmpeg ได้ไหม
2. ตำแหน่ง/มุมที่จะติดกล้อง และจะครอบคลุมกี่โต๊ะ
3. ช่วงทดลองต้องการเสียงแจ้งเตือนไหม หรือเก็บสถิติเงียบๆ อย่างเดียว
4. ยอมรับการแก้แบบเพิ่มอย่างเดียวใน `CameraStage` (ขั้น 3) และ `vite.config.ts` (ขั้น 1) ไหม
